# ras_arm_ws: Gazebo simulation of the 6-axis arm (RAS Build Challenge 2026, Project 3)

Team **engineers over engineering**. Target: Ubuntu 22.04, ROS 2 Humble, **Gazebo Fortress** (`ros_gz` + `ign_ros2_control`).

> **Tested / not tested.** The offline analysis (static torque, workspace, clearance, offline dynamic simulation, all
> figures, the LaTeX section) was run and its outputs are in `sim_evidence/`. `check_urdf` passes on the cleaned URDF.
> **Gazebo, `colcon build` and the ROS nodes were not run**: the build machine had no ROS 2 or Gazebo.
> See "What was tested" at the end before relying on the Gazebo part.

## 1. Install

```bash
sudo apt update
sudo apt install ros-humble-ros-gz ros-humble-ign-ros2-control ros-humble-ros2-control ros-humble-ros2-controllers \
  ros-humble-xacro ros-humble-robot-state-publisher ros-humble-joint-state-publisher-gui ros-humble-rviz2 \
  python3-colcon-common-extensions python3-numpy python3-scipy python3-matplotlib python3-yaml python3-opencv
pip install pin        # pinocchio: only needed for the offline simulation and the cross-check
```

`ros-humble-ros-gz` installs Gazebo Fortress next to anything already present (Gazebo Classic 11 can stay). If `ign gazebo --version`
is missing afterwards, add the OSRF repository and install it directly:

```bash
sudo curl https://packages.osrfoundation.org/gazebo.gpg --output /usr/share/keyrings/pkgs-osrf-archive-keyring.gpg
echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/pkgs-osrf-archive-keyring.gpg] http://packages.osrfoundation.org/gazebo/ubuntu-stable $(lsb_release -cs) main" | sudo tee /etc/apt/sources.list.d/gazebo-stable.list
sudo apt update && sudo apt install ignition-fortress
```

## 2. Build

```bash
cd ras_arm_ws
source /opt/ros/humble/setup.bash
colcon build --symlink-install
source install/setup.bash
```

## 3. Run

| What | Command |
|---|---|
| Start the simulation | `ros2 launch robotic_arm_gazebo sim.launch.py` (add `headless:=true` for server only) |
| Run the demo (homing + 4 cycles, logged) | `ros2 launch robotic_arm_control demo.launch.py` |
| Demo with screenshots and clip | `ros2 launch robotic_arm_control demo.launch.py cycles:=2 record:=true video_seconds:=50.0` |
| E-stop test (pick, hold, press) | restart the simulation, then `ros2 launch robotic_arm_control demo.launch.py estop_test:=true` |
| Generate all figures + LaTeX | `ros2 run robotic_arm_analysis make_figures --out ~/sim_evidence` |
| Same without ROS/Gazebo (offline) | `cd src/robotic_arm_analysis && python3 -m robotic_arm_analysis.make_figures --offline --out ../../sim_evidence` |
| RViz view with sliders | `ros2 launch robotic_arm_description display.launch.py` |

Run the demo in a second terminal (after `source install/setup.bash`) once the four controller spawners have finished.
Restart the simulation between two demos (the cubes are then back at their start positions).

- Logs go to `~/ras_arm_logs/<date_time>/` (`cycle.csv`, `estop.csv`, `events.csv`, `meta.json`).
- `make_figures` uses the newest complete Gazebo run and the newest E-stop run found there; with no Gazebo log it runs the
  offline simulation instead. The data source is written in the first line of `simulation_section.tex` and the text adapts to it.
- **Clip:** `record:=true` writes `~/ras_arm_logs/media/pick_place.mp4` (1280x720, 30 fps, from the fixed cell camera, starting at the
  first APPROACH), plus `gazebo_world.png` (first frame) and `gazebo_arm.png` (first GRASP). Screen-capture alternative:
  `ffmpeg -video_size 1920x1080 -framerate 30 -f x11grab -i :0.0 -t 50 -c:v libx264 -pix_fmt yuv420p pick_place.mp4`.
- Manual E-stop at any time: `ros2 service call /estop std_srvs/srv/SetBool "{data: true}"` (release with `false`).
- Copy `sim_evidence/images/sim/*` to `images/sim/` of the book and `\input{simulation_section.tex}`.

## 5. URDF fixes and name mapping

| Problem | Fix |
|---|---|
| Joints locked | ranges, efforts, velocities, damping and friction set (table below) |
| Y-up model | `world` link + fixed joint `world_to_base` (xyz 0 0 0.056, rpy -1.5708 0 3.0523): arm upright, base bottom on the table top, world origin at the base centre |
| J4/J5 names swapped | joint and child-link names swapped, geometry untouched (mesh files renamed with the links) |
| Axis tilts, rpy offsets | kept as exported. The three pitch axes (J2, J3, J4) are exactly parallel in the world frame, so the 5 deg tilt is a constant yaw offset of the arm plane; it is absorbed in the base yaw and has no effect on torques, reach or clearance. The roll axis J5 is 1.8 deg off the link axis; it is part of the model, so every result includes it |
| Package name | `robotic_arm_description`, all `package://` paths updated |
| ROS 1 launch files | replaced by `display.launch.py`, `sim.launch.py`, `demo.launch.py` |
| Heavy meshes | visual: original STL; collision: convex hull of each link simplified to about 200 faces (84 kB in total). Quadric decimation of the raw meshes was tried and rejected: they are assemblies of many separate parts and break apart |
| Masses / inertias | masses unchanged. All 7 inertia tensors are valid (positive definite, triangle inequality): nothing corrected |
| No gripper joint | two prismatic jaws added (`left_jaw_joint`, `right_jaw_joint`, 30 mm stroke each, 2 x 10 g added mass) + `tcp` frame. Grasp by the Fortress `DetachableJoint` system (see below) |

| Joint | Final joint name | Export joint name | Child link (final) | Mesh file (export) | Range (deg) | Effort (N·m) | Max speed (deg/s) |
|---|---|---|---|---|---|---|---|
| J1 | `base_rotation_joint` | `base_rotation_joint` | `shoulder_link` | `shoulder_link.STL` | ±170 | 3.9 | 129 |
| J2 | `shoulder_lift_joint` | `shoulder_lift_joint` | `upper_arm_link` | `upper_arm_link.STL` | ±100 | 3.9 | 129 |
| J3 | `elbow_joint` | `elbow_joint` | `forearm_link` | `forearm_link.STL` | ±135 | 3.9 | 129 |
| J4 | `wrist_pitch_joint` | `wrist_roll_joint` | `wrist_pitch_link` | `wrist_roll_link.STL` | ±135 | 3.9 | 129 |
| J5 | `wrist_roll_joint` | `wrist_pitch_joint` | `wrist_roll_link` | `wrist_pitch_link.STL` | ±135 | 1.96 | 400 |
| J6 | `tool_rotation_joint` | `tool_rotation_joint` | `tool_flange_link` | `tool_flange_link.STL` | ±135 | 1.96 | 400 |

**Grasp choice.** A 50 g cube held by friction between two box jaws is unreliable in the DART physics of Fortress (it slips or is
ejected, depending on contact parameters). The jaws therefore close to 1 mm clearance per side for the picture, and the cube is held
by a `DetachableJoint` (fixed joint created on the attach topic, removed on the detach topic). The friction grip is checked by
calculation in the torque table instead.

**Inverse kinematics.** A damped least-squares solver on the URDF chain (`kinematics.py`, numpy only): it copes with the exported
axis tilts and the 91 mm lateral wrist offset without a hand-derived model, and needs no MoveIt configuration. It was checked against
pinocchio on 500 random poses (difference below 1e-14).

**Control.** All joints use the effort interface with a PID in the joint trajectory controllers. This is what allows the E-stop to
remove the torque of J1 to J4 (controller deactivated, effort forced to 0) and makes the logged effort the actuator torque.

## 6. Assumptions (edit `task.yaml` / `clean_urdf.py`)

- Payload: 30 mm cube, 50 g. Gripper friction coefficient 0.5, pinion radius 10 mm.
- Layout (world origin = base centre on the table top): pick stand 50 x 50 mm, top at z = 185 mm, at r = 200 mm, azimuth 0;
  bins 90 x 90 mm, floor at 140 mm, rim at 180 mm, at r = 210 mm, azimuth ±80 deg. Tcp heights: grasp 205 mm, travel 260 mm, release 225 mm.
  Tool tilted 10 deg from vertical, jaws at 150 deg to the radial direction (the cube is fed with that yaw). One arm configuration
  for the whole cycle; lift, rotate J1 at the travel height, descend.
  **These raised, close-in stations are a result of the torque and clearance study, not a free choice.**
- Joint ranges: assumed (table above). The CAD meshes show no interference on the path (non-adjacent links stay 34 mm apart) and
  neighbouring links sit side by side, so the meshes do not set tighter limits; cable and gearbox stops are not modelled.
  The task needs J4 up to 115 deg and J5 at -34 deg. J1 is limited to ±170 deg (it was `continuous`). J5/J6 assume the 270 deg DS3218MG.
- Stepper joints: planned speed 60 deg/s, acceleration 120 deg/s² (assumed), damping 0.1 N·m·s/rad, unpowered friction 0.3 N·m
  (17HS4401 detent torque 0.022 N·m x 14). Servos: planning speed 120 deg/s, friction 0.2 N·m. Gearbox efficiency 0.70 is inside the 3.9 N·m.
- Homing: virtual switches 12 to 20 deg from the start pose, seek speed 8 deg/s, back-off 5 deg.
- Start pose: "balanced" pose (J2 3.3, J4 -28.6 deg), where gravity torques of J2 to J4 vanish, so the unpowered arm stays put.

## 7. Troubleshooting

- **Arm invisible / "Unable to find uri[package://robotic_arm_description/...]"**: Gazebo resolves `package://` through
  `IGN_GAZEBO_RESOURCE_PATH`, which `sim.launch.py` sets to `install/robotic_arm_description/share`. If you start Gazebo by hand:
  `export IGN_GAZEBO_RESOURCE_PATH=$(ros2 pkg prefix robotic_arm_description)/share`. (`GAZEBO_MODEL_PATH` is the Classic variable and is not used.)
- **Black window, crash at start, or no camera images (VM, old GPU)**: `export LIBGL_ALWAYS_SOFTWARE=1` before launching, or run
  `headless:=true`. To use ogre 1: `ign gazebo --render-engine ogre` and set `<render_engine>ogre</render_engine>` in the world. Without rendering, `record:=true` gives nothing.
- **Slow (real-time factor below 1)**: visual meshes are 39 MB; use `headless:=true` for logging runs.
- **Controllers do not start**: check `ros2 control list_controllers`; the plugin needs `ros-humble-ign-ros2-control`. If your version
  only ships the `gz_` names, replace `ign_ros2_control-system` / `ign_ros2_control::IgnitionROS2ControlPlugin` /
  `ign_ros2_control/IgnitionSystem` in `clean_urdf.py` by `gz_ros2_control-system` / `gz_ros2_control::GazeboSimROS2ControlPlugin` / `gz_ros2_control/GazeboSimSystem`.
- **Arm sags at start-up**: the installed plugin ignored `initial_value`, or cubes were attached at start (Fortress older than the
  `<initial_attach>` option). Start the demo immediately after the spawners; the node sends a detach to every cube first.
- **Cube is not picked**: your Fortress has no `attach_topic` in DetachableJoint (it is in the current ign-gazebo6 sources; run `sudo apt upgrade` to get the latest Fortress).
- **Cubes 2 to 4 are not fed**: the node calls `ign service -s /world/sorting_cell/set_pose`; `ign` must be on the PATH.
- **Effort plots are zero**: `meta.json` tells which effort source was logged; update `ros-humble-ros2-controllers` so that
  `/stepper_controller/controller_state` carries `output.effort`.
- **Oscillation in Gazebo**: lower the `d` gains in `controllers.yaml` first (they were tuned on the offline model at 1 kHz).
